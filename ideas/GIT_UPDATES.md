I'd do exactly that. In fact, I think it will make your version history considerably cleaner as the project grows.

What you're describing is essentially a release-based workflow:

* Development contains all individual commits.

* A PR documents the overall release.

* Main receives the merged changes.

* One official version tag identifies the release.

You don't need to tag every individual development commit.

### 1\. How I'd handle v0.5.0

Suppose you make these commits on `development`:

```text

world: add map overlay
character: add equipment stats
inventory: implement tab overlay
ui: improve mobile navigation
entities: update interaction handling
```

You then create one PR.

### 2\. What happens to the commit history?

I'd select Create a merge commit when merging the PR.

Your main branch history would look conceptually like this:

```text
main
│
├── Merge pull request #13
│   v0.5.0 — World & Character Update
│
├── Previous commits
│
└── v0.4.11
```

The individual commits from development remain in the history.

You can still inspect each commit, see its message, and examine exactly what changed.

Then tag the merge commit:

```bash
git switch main
git pull origin main

git tag -a v0.5.0 -m "World & Character Update"
git push origin v0.5.0
```

Your tag now identifies the completed release.

### 3\. Your version history

I'd retain your existing detailed tags for historical releases, but going forward, I'd distinguish between development commits and official releases.

For example:

| Version   | Description                   |
| --------- | ----------------------------- |
| v0.4.11   | Previous stable release       |
| v0.4.11.1 | Historical incremental update |
| v0.4.11.2 | Historical incremental update |
| v0.4.11.3 | Historical incremental update |
| v0.5.0    | World & Character Update      |

You don't have to change or delete any existing tags.

One detail: Git sorts version tags lexicographically unless you request version sorting. So your current `git tag -n` output isn't necessarily chronological. You can use:

```bash
git tag -n --sort=version:refname
```

### 4\. I'd also use GitHub Releases

This is the one additional thing I'd recommend.

After merging and tagging `v0.5.0`, go to GitHub → Releases → Draft a new release.

New release

Recommended

Choose a tag: `v0.5.0`

Release title:

`v0.5.0 — World & Character Update`

Release notes:

Use the same combined change list from your PR.

GitHub Release example

This gives you a proper release page with:

* Version number.

* Release description.

* Combined change list.

* Source code ZIP and TAR.GZ automatically generated by GitHub.

* Links to the corresponding tag and commit.

PR and Release serve different purposes: the PR documents and reviews the integration of development work; the Release announces the completed version.

### 5\. My recommended final workflow

* Develop

    Work exclusively on `development`. Use `uk "description"` for commits.

* Prepare release

    When ready, create PR `development` → `main`.

    Title it `v0.5.0 — World & Character Update`.

* Merge

    Use Create a merge commit. Individual commit messages remain available.

* Tag

    Tag the resulting main commit as `v0.5.0`.

* Publish

    Create the GitHub Release using the PR's combined change list.

* Continue development

    Keep working on `development` for the next update.

One small maintenance step after merging: synchronize `development` with `main` so the merge commit and release tag are included in its history.

I particularly like this approach for your project because it preserves your detailed commit history without requiring you to maintain a tag for every little change. Your version numbers become meaningful milestones rather than a record of every coding session.
